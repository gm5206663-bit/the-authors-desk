# Authority and current state

## Classify before you act

| Class | How to use it |
|---|---|
| Explicit author instruction / recorded user lock | Preserve wording, date and evidence. Respect its exact scope; follow the project's conflict rules. |
| Delegated design | Record the delegation and its limits. Do not label it a verbatim user lock. |
| Local rails, foundation and domain owner | Use the project's declared hierarchy; domain ownership can matter more than file date. |
| Current-state owner | Read from the registry's paths and local contract, at a recorded revision. Resolve epoch/acceptance, not just file numbering. |
| Generated view | Regenerate from its declared owner. Do not fix a number only in the view. |
| Proposal / draft / candidate | Not accepted history or permission to publish. Approval of one field does not approve its neighbors. |
| Historical snapshot / identity edition | Evidence of that date. It does not automatically supply current ranks, chapter edges, repo names or blockers. |
| Source summary / inference | Label provenance and uncertainty. Neither is a user instruction. |

This table does not replace a serial's more specific hierarchy. For example,
Supergirl declares separate owners for accepted chapter state, author wording,
relationships, knowledge, abilities and chronology. Read its local contract.

## Conflict procedure

1. Capture both claims with repository, path, revision, location and source type.
2. Read the applicable local authority chain, amendments and author evidence.
3. If a stronger explicit source resolves the conflict, repair the stale view
   within authorization, regenerate dependent views and leave a dated receipt.
4. If approval, meaning or source scope remains unclear, record the unresolved
   question and stop the dependent action. Do not select the convenient claim.
5. Do not "refresh" historical quotations or signed editions to remove a conflict.

Use the [decision template](templates/DECISION.md). Keep existing author-lock and
open-decision records as their canonical homes; link to them, do not create a
competing account-wide decisions database.

## Loading Sara safely

Read Sara's root `AGENTS.md`, `SARA.md`, operating profile and relevant incarnation
for behavior and lineage. The operating profile is dated 2026-09-15 and includes
project snapshots. Its old Fire Phoenix checkpoint is not today's checkpoint.
Load the live serial's own manifest/panel and approval record before story work.
The onboarding layer does not edit, erase or silently modernize those editions.

## Signs that are not acceptance

Highest chapter filename; a shipped shelf copy; a green pinned-baseline CI run;
a count in a README; a draft delivered in chat; a readiness recommendation; an
agent's confident voice. Verify the actual local acceptance source.
